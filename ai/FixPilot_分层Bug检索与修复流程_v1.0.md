# FixPilot Bug 检索与修复流程 v1.1

> **一句话定位**：先广撒网做通用排查（70%），不预设任何种子，按检查矩阵逐类主动扫全库；扫出的每个 Bug 才作为种子，切到分层扩大流程（30%）顺藤摸瓜挖同类项。
>
> **给谁用**：任何接手本项目的 AI（CodeBuddy / Trae / 其他）。无需了解历史上下文，照着执行即可。
>
> **前置要求**：先读 [`../AGENTS.md`](../AGENTS.md) 和 [`WORK_LOG.md`](WORK_LOG.md)，遵守其中的读源码、追加日志、不猜、不泄密纪律。

---

## 0. 为什么这么分

Bug 检索有两种动力源：

- **被动锚定**：已知一个 Bug，从它出发找同类。优点是精准，缺点是**只能发现已知模式的变种**——你不知道的 bug 类型永远扫不到。
- **主动通用排查**：不依赖任何已知 Bug，按一张覆盖常见 bug 类别的检查矩阵逐类扫库。能发现"你根本没想到会有"的问题。

本项目由多个 AI 接力开发，不同 AI 的坏习惯、重复实现、编码问题散落各处，单靠锚定会漏掉大片盲区。所以**通用排查是主体（70%），锚定扩大是收割手段（30%）**。顺序固定：先 Phase A 主动扫，扫到的 Bug 进 Phase B 分层扩大。

---

## 1. 硬性纪律（全程不可跳过）

1. **只认源码**：所有结论必须有文件路径 + 行号 + 代码原文佐证。禁止凭界面文字、截图、文档描述猜测行为。文档是规格，不是证据。
2. **区分可信度**：每个发现标注 `[已确认]` / `[已验证]` / `[高风险未验证]` / `[需人工补测]`。
3. **修一个验一个**：每修一个 Bug 当场验证（编译 / 运行 / 浏览器），通过才进下一个。不准攒一批最后一起验。
4. **先报告后动手**：Phase A 是纯检索，发现 Bug 只报告不动手。修复统一放到 Phase B 的 Layer 3，除非已获明确授权。
5. **追加 WORK_LOG**：整轮结束按 `WORK_LOG.md` 模板追加汇总。不准覆盖或删除历史条目。
6. **不动 .workbuddy/**：`.workbuddy/` 是本地工作区数据，不跟踪、不提交、不删除。
7. **改前确认基线**：动手改前先 `git status` + `git log -1`，确认在最新代码上改。

```

  ▼

  │
  ▼

```

| 阶段 | 性质 | 输入 | 产出 |
|------|------|------|------|
| Phase A 通用排查 | 主动、不预设 | 检查矩阵 | Bug 清单（带分类+严重程度+可信度） |
| Phase B 分层扩大 | 被动、以 Bug 为种子 | Phase A 的 Bug 清单 | 同类项+变体+修复+回归结论 |

## 3. Phase A — 通用排查（主体，70%）

**执行方式**：逐类过下面的检查矩阵。每类先列"查什么"，再给"怎么查"（grep 模式 / 代码位置），再给"红旗"（什么样的代码值得怀疑）。每发现一个疑似，读源码确认，记入 Bug 清单，**不修**。

**覆盖原则**：宁可多记疑似、交人复核，也不要因"看起来应该没事"就跳过。Phase A 的价值在于覆盖面，不在于精准度。

### A1. 字符编码与中文完整性

**为什么查**：多 AI 接力 + Windows 环境，中文常量写入时编码损坏的先例已有（safety.py P1）。这类 bug 静默——代码能跑，但用户看到乱码或问号。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| .py 中文常量是否损坏 | 扫所有含中文的字符串字面量，检查是否有 `?` 替代 | `"?{5,}"` 连续问号串 |
| JSON 响应中文 | 查所有 `json.dumps` 是否漏 `ensure_ascii=False` | 返回给前端的 JSON 里中文被转义成 `\uXXXX` |
| 文件读写编码 | `open()` 是否显式指定 `encoding="utf-8"` | 裸 `open(path)` 在 Windows 默认 GBK |
| HTML charset | index.html / share.html 是否声明 `<meta charset="utf-8">` | 缺声明导致中文乱码 |
| 模板读入编码 | `f.read_text(encoding=...)` 是否一致 | 不同文件用不同编码读 |

### A2. 真值判断与空值兜底

**为什么查**：JS 里 `""`/`0`/`null`/`"???"` 的真值行为是 bug 重灾区。前端 `||` 被损坏值穿透的先例已有。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| `x \|\| fallback` 兜底 | grep `\|\|` in app.js | x 是 truthy 但语义损坏（如 `"?????"`）时穿透 |
| `x ?? fallback` | grep `??` | 只挡 null/undefined，不挡空串/损坏值 |
| `if (x)` 隐式真值 | grep `if \(` | `0` / `""` 被当 falsy 跳过 |
| 后端 `or` 兜底 | grep ` or "` / `or default` in .py | 同 JS `\|\|` 问题 |
| 前后端对"空"定义不一致 | 比对：后端返回 `None`/`""`/缺失 key，前端怎么判 | 后端省略 key，前端 `obj.x \|\|` 还能兜；后端传 `""`，前端 `\|\|` 就失效 |

### A3. 前后端契约对齐

**为什么查**：本项目前端原生 JS、后端 FastAPI，没有共享类型。枚举、文案、校验规则容易各维护一份且不对齐。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| 枚举值两端是否一致 | 后端 `{"normal","roast","concise"}` vs 前端选项 | 一端加了新值，另一端没同步 |
| 用户水平枚举 | `beginner/intermediate/advanced/unknown` 两端比对 | 同上 |
| 风险等级 | `medium/high` 两端比对 | safety.py 与 app.js RISK_NOTICES 文案是否一致 |
| 校验正则 | 后端用户名正则 vs 前端校验 | 一严一松导致绕过 |
| 错误码/HTTP 状态 | 后端抛 401/402/403/404，前端是否都处理 | 漏处理某个状态码 → 静默失败 |

### A4. 多 AI 重复实现与行为不一致

**为什么查**：接力开发时，不同 AI 可能各自实现同一逻辑（检索、校验、格式化、兜底），行为不一致。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| 同一逻辑多份实现 | 找功能相似的函数（如多个 `_content_to_text`） | 行为不同 → 用哪个不确定 |
| 两套常量各一份 | 前后端各维护 risk/枚举文案 | 已确认 safety.py + app.js 各一份 |
| 重复的 db 文件 | 检查 `fixpilot.db` 是否有多份 | backend/ 和 app/ 各一个，确认哪个在用 |
| 规则文档两套 | ai/ 下是否有中英双版本说同一件事 | Safety_Compliance_Governance(英) vs 合规与安全治理(中) 是否同步 |

### A5. 注入与越权

**为什么查**：SQLite 手拼 SQL + 原生 JS innerHTML + 邀请码鉴权，是注入和越权高发区。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| SQL 拼接 | grep `f"SELECT` / `+ str` / `% ` in db.py | 未参数化的用户输入拼进 SQL |
| XSS | grep `innerHTML` in app.js | 用户/模型文本未 escapeHtml 直接 innerHTML |
| 鉴权检查 | 每个 API 路由是否调 `_require_auth`/`_require_admin` | 漏鉴权的路由 |
| 越权 | 会话/邀请码归属校验（`conv["invite_code"] != owner`） | 用户 A 能读用户 B 的会话 |
| 密钥泄露 | grep `API_KEY` / `SECRET` / `password` | 写进日志、响应、WORK_LOG |
| 分享链接越权 | `/api/share/{token}` 是否真的只读 | 能通过 share token 改数据 |

### A6. 流式与协议正确性

**为什么查**：SSE 流式聊天是核心体验，标记配对、中断恢复、部分 token 都容易出问题。WORK_LOG 已记录多次流式相关修复。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| `__start__`/`__end__` 配对 | 检查 gen() 异常路径是否都会发 `__end__` | 异常时只 yield `__error__` 不发 `__end__` |
| 前端 SSE 解析 | app.js 怎么 split data 行 | 多行 data / 空行 / 不完整 chunk |
| 中断恢复 | 连接断开时前端状态 | acc 残留、loading 不消失 |
| 风险标记流式解析 | `might_be_risk_directive` 边界 | 短前缀误判、长前缀漏判 |
| joke 标记同理 | `might_be_joke_directive` | 同上 |
| share.html 流式兼容 | 分享页是否依赖流式协议 | 分享页拿到的是存库的完整文本，不是流 |

### A7. 错误吞没与降级兜底

**为什么查**：`except: pass` 式吞异常会让 bug 永远沉默。OCR/LLM 失败兜底不当时用户看到空白。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| 裸 except | grep `except` in .py | `except Exception` 后只 pass / 只 log 不告知用户 |
| OCR 失败 | service.py `_content_to_text` 的 except | 失败时返回什么，用户能否理解 |
| LLM 空回复 | main.py gen() 的 `if not full` | 空回复是否有恢复消息 |
| LLM 异常 | gen() 的 except 分支 | 错误消息是否含敏感信息 |
| 知识库加载失败 | knowledge.py load_chunks | 文件不存在时是否崩溃还是降级 |

### A8. 并发与启动时序

**为什么查**：FastAPI 多 worker + SQLite + 模块级初始化（`_chunks = load_chunks()` / `db.init_db()`），时序和并发是隐患。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| 模块级副作用 | main.py 顶层 `_chunks`/`init_db`/`bootstrap_admin` | import 时执行，测试/多 worker 时重复 |
| SQLite 写并发 | db.py 写操作是否加锁 / WAL | 多请求同时写 → database locked |
| 全局可变状态 | grep 全局变量 | 请求间共享导致串数据 |
| init_db 幂等 | 重复调用 init_db 是否安全 | 重复建表/插管理员报错 |

### A9. 边界与输入校验

**为什么查**：配额（-1 不限）、过期时间、用户名、图片大小等边界值容易出 off-by-one 或漏校验。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| 配额 -1 不限 | `quota_total == -1` 的所有判断分支 | 某处漏判 -1 当成 0 |
| 过期时间 | `expires_at` None vs 有值 | None 当成已过期 or 有值被跳过 |
| 用户名/密码校验 | 后端正则 + 长度 | 前端校验能被绕过，后端是否兜底 |
| 图片输入 | OCR 对超大图/非图片/损坏图 | 崩溃还是降级 |
| 消息历史截断 | `[-16:]` 截断 | 截断点在多模态消息中间会丢图片 |

### A10. 死代码与残留物

**为什么查**：调试残留、被 .gitignore 的临时文件、重复资源，是项目卫生问题，也藏着隐患。

| 查什么 | 怎么查 | 红旗 |
|--------|--------|------|
| 根目录临时文件 | `_mktest.py` / `_test_joke.py` | 调试残留，已 gitignore |
| 重复 db | `fixpilot.db` 多份 | 用错 db 导致数据丢失 |
| 未使用函数 | 找只定义不调用的函数 | 死代码误导后续 AI |
| 旧 SYSTEM_PROMPT | llm.py `SYSTEM_PROMPT` 标注"保留名称避免旧调用失效" | 是否还有调用方，没有则删 |
| .trae 残留 | `.trae/documents/account-binding-system.md` | 是否已落地，还是过期设计稿 |

## 4. Phase B — 分层扩大（30%，以 Phase A 发现的 Bug 为种子）

**触发条件**：Phase A 产出了 Bug 清单。对每个 Bug（或同类 Bug 合并）跑一次下面的分层流程。

**核心原理——Bug 传染性**：一个错误在库里大概率有同类项，因为：① 同一 AI 的坏习惯会重复；② 复制粘贴会传播；③ 多 AI 各写一套不对齐；④ 一个误解会泛化到所有用到它的地方。

### Layer 0 — 锚定种子

**输入**：Phase A 的一个 Bug。

1. **根因链**：连问三个为什么（直接原因 → 写入原因 → 漏检原因）。
2. **提炼 Bug 模式**：去掉业务细节，抽象成可搜索的描述。
   - 格式：`模式名 | 特征（怎么识别） | 为什么是 Bug`
3. **列搜索维度**：文件类型 / 模块 / 同源 commit / 镜像（前后端对应实现）。

**输出**：Bug 模式卡 + 搜索维度。

### Layer 1 — 同模式横扫

**输入**：Layer 0 的模式卡。

1. **逐维度搜索**：正则 / 关键词扫全库 + 同源追溯（`git show <hash> --stat` 看同 commit 还改了啥）+ 镜像比对（前端有后端有没有）。
2. **逐个验证**：读源码确认真的命中模式，不只看关键词命中。
3. **分级**：标 P0–P3 + 可信度。

**输出**：同类 Bug 清单。无新发现也明确记录"同模式横扫未发现其他实例"。

### Layer 2 — 根因升华与变体扫描

**输入**：Layer 1 的全部 Bug。

1. **上溯根因**：从多个实例找共性，提炼比"模式"更高一层的"错误观念/假设"。
2. **搜变体**：同根因不同表现。常见变体对照：

| 根因类别 | 原模式 | 可能变体 |
|----------|--------|----------|
| 真值兜底误判 | `x \|\| f` | `??` / `if(x)` / `x?x:f` |
| 编码损坏 | .py 中文 | .js/.html/.md 中文 / ensure_ascii |
| 前后端不对齐 | risk 文案 | 所有前后端各一份的常量 |
| 多 AI 重复实现 | safety 两套 | 检索/校验/格式化是否也各一套 |

**输出**：变体 Bug 清单。上溯到最抽象层且无新发现则终止。

### Layer 3 — 修复回归与防御加固

**输入**：Layer 0–2 全部 Bug。

1. **修复**（按严重程度高→低）：最小改动，改完当场验证，先 `git status` 确认基线。
2. **纵深防御**：对每个根因类别加一道运行时防线（写进代码，不是文档）。例：`safeRiskCopy` 排除损坏值。
3. **回归三查**：① 直接回归（核心流程没坏）；② 依赖检查（有没有代码依赖原 Bug 行为）；③ 防御副作用（新防线有没有误伤正常输入）。
4. **追加 WORK_LOG**。

**输出**：修复记录 + 回归结论 + 剩余风险。

## 5. 举一反三工具箱（Phase B 每层通用）

| 方法 | 怎么用 | 示例 |
|------|--------|------|
| **模式抽象** | 具体 Bug → 去业务词 → 留代码结构特征 | 中文变 ? → 硬编码中文常量编码损坏 |
| **根因上溯** | 直接原因 → 为什么 → 更深 → 还会导致什么 | `\|\|` 被骗 → 真值兜底未排除损坏值 → 所有真值判断兜底 |
| **镜像检查** | A 处有 → B 处对应实现有没有 → 第三处（配置/文档） | 后端 risk 文案 → 前端 → 文档描述 |
| **同源追溯** | Bug 在 commit X → X 还改哪些文件 → 逐个查 | `git show 16403f8 --stat` 列 8 文件 |
| **传播路径** | Bug 输出流向哪 → 每跳有无防御 | safety.py → main.py → app.js 三跳各查 |

## 7. 终止条件

整轮检索在以下任一条件满足时结束：
1. Phase A 的 10 类全部过完，且 Phase B 对每个已确认 Bug 都跑完了 Layer 0–3。
2. Phase B 连续两层无新的未修复 Bug。
3. 剩余发现全部是 `[需人工补测]`，自动化到极限。

结束后必做：汇总追加 `WORK_LOG.md`——种子 Bug、各层发现、修复清单、验证结果、剩余风险。不准只修不记。

## 8. 真实示例（safety.py P1 演示 Phase B 全流程）

> 此例演示 Phase B 如何以一个 Bug 为种子走完四层。Phase A 主动扫出这个 Bug 后，按此扩大。

- **种子**：`safety.py` `_RISK_NOTICES` 中文全损坏为 `?`，`app.js` `||` 兜底被穿透。commit `16403f8`。
- **Layer 0**：模式"硬编码中文常量编码损坏 + 真值兜底未排除损坏值"。维度：同 commit 8 文件 / 全库中文常量 / 所有 `||` 兜底 / 前后端各一份常量。
- **Layer 1**：查 `git show 16403f8 --stat` 的 8 文件中文；全库 grep `||` 兜底逐处判；前后端常量比对。
- **Layer 2**：根因"前后端各维护常量未对齐 + 兜底只考虑缺失未考虑损坏"。变体：所有真值兜底（`??`/`if(x)`）、所有前后端各一份常量。
- **Layer 3**：修复 safety.py 中文（`729f349`）+ 前端 `safeRiskCopy` 防线 + 回归验证。剩余风险：其他前后端各一份常量是否需统一数据源。
