## 0. 一句话总览（给接手者）

FixPilot 是一个**面向普通人的「电脑故障排查」专属 AI 助手**，用「医生问诊」式的一问一答，一次只推进一个关键判断题，逐步把蓝屏、黑屏、无法开机、闪退、网络异常等故障定位并解决。它**不是通用大杂烩助手**，刻意只做好「电脑坏了怎么办」这一件事。有一定毒舌冷幽默人格。当前为纯后端服务 + 原生前端，支持邀请码/账号登录、次数配额、对话分享、知识库检索（RAG）、图片 OCR 识图。

## 1. FixPilot 是什么

### 产品的一句话定位
**电脑故障排查 AI 助手**：像医生问诊一样，通过一问一答，一次只解决一个电脑问题。

### 核心使用场景
- 电脑蓝屏、卡死、无法开机、黑屏、花屏、闪退、鼠标卡顿、没声音、连不上网、装系统/重装系统、系统优化等故障排查。
- 用户描述症状 → AI 一次问一个关键判断题 → 逐步定位 → 给出精简操作步骤。

### 主要目标用户
- 面向朋友/熟人的小范围使用，非公开大规模产品。
- 用户按电脑水平大致分三类：不太懂的小白、会折腾一点的中级、较熟的专家级（见第 6 节，该分类**尚未落入代码**）。
- 用户可通过邀请码（限制次数/有效期）或绑定账号密码登录。

### 用户最典型的使用路径
1. 打开登录页 → 用邀请码（6 位）登录，或账号密码登录。
2. 进入主界面 → 出现欢迎语（问候 + 提示 + 快捷问题 chips）。
3. 输入/点选问题，或上传蓝屏/报错截图 → AI 问诊式一步步引导。
4. 问题解决后，可把对话**生成长图**或**复制只读分享链接**发给别人。
5. 左侧会话列表可切换/新建多个独立对话。

### FixPilot 希望解决什么问题
- 很多人电脑出问题后第一反应是发帖求助，等半天没人理，或被「重装系统」这类通用答案打发。
- FixPilot 想做到：记得用户一步步描述的症状，一次只问一个关键问题，把问题定位到根；不追求「什么都会」，专注把「电脑坏了怎么办」做好（这段也是「关于我们」页的官方文案）。

### 与普通通用 AI 聊天工具相比，当前设计上的核心区别
- **交互式问诊**：强制一次只问一个判断题，不一次性罗列完整排查流程，不写长教程（System Prompt 硬性约束，见第 4、5 节）。
- **专属知识库（RAG）**：基于一份电脑故障转写稿，用 BM25 检索相关知识块，回答优先依据知识库，不编造。
- **图片 OCR 识图**：能识别截图里的文字（蓝屏代码、报错信息），不能真正"看图"（见第 3 节）。
- **毒舌但专业的人格**：只在用户犯低级错误时损两句，且损完立刻给下一步（见第 5 节）。
- **配额与分享体系**：邀请码限流、剩余次数显示、对话长图/链接分享。
- **刻意克制**：不堆功能、够用就好（官方文案原话）。

### 新建对话流程
- 点「新建对话」→ 后端创建 conversation（id 形如 `c` + 16 位 hex），前端置为当前会话并渲染欢迎页。
- 标题：首次提问时，后端 `POST /api/title` 取问题前 12 字设为标题。
- 会话存储在**后端 SQLite**，非 localStorage。

### 历史对话
- 左侧「最近对话」列表，按 created_at 倒序。点击切换，删除按钮直接删会话（级联删消息）。【已实现】
- 会话归属：邀请码用户按 `invite_code`，管理员按 `admin:username`（见第 7 节）。

### 图片上传
- 前端：选图 → 压缩到 max 1280px（jpeg 0.85，超 1MB 降质量）→ 再生成 480px 缩略图（≤60KB）缓存到历史。
- 后端：收到图片 dataURL → RapidOCR 本地离线识别文字 → 把识别文字作为 `[用户上传图片中的文字]` 注入给模型。【已实现】
- 欢迎页会提示：只能识别截图里的文字，不能判断硬件外观/接线（见第 5 节冲突说明）。

### 快捷问题
- 欢迎页底部 4 个 chips：游戏经常闪退 / 开机黑屏 / 鼠标卡顿 / 没有声音。点击直接作为问题发送。【已实现】

### 设置入口
- 顶栏齿轮按钮 → 设置弹窗（账号/API/关于我们）。【已实现】
- 模型选择器中的「自定义...」→ 直接打开设置的 API 标签页。【已实现】

### 首次使用流程（当前）
- 登录 → 直接进入主界面 → 欢迎页问候 + 提示 + 快捷 chips → 用户输入就开始问诊。
- **没有**水平问卷、**没有**语气选择（这两项是已确定但未实现，见第 6 节）。

### 当前已经存在的所有用户偏好设置

- 自定义 API 配置（localStorage `fixpilot_api_settings`：provider/apiKey/apiBase/model）。

## 3. AI 当前真实能力

> 本节严格区分「模型理论上可能做到」与「FixPilot 产品现在实际开放给它做到」。

### 能识别图片吗
- 能（仅限文字）。图片会走 OCR 把文字提取出来再喂给模型。【已实现】
- 底层依赖：RapidOCR（rapidocr-onnxruntime），本地离线，支持中文，onnxruntime 固定 1.20.1（版本冲突教训）。

### 图片具体能看到什么
- 只能看到 OCR 识别的**文字**（按行拼接）。**看不到**图片的视觉内容（颜色、图形、硬件外观、接线、屏幕画面等）。
- 上传的图片若来自网络（无 base64），模型只会看到「（用户上传了一张图片）」占位。
- 图片中无文字 → 模型看到「（图片中未识别到文字）」。
- OCR 失败 → 模型看到「（图片识别失败：...）」，不阻断对话。

### OCR 能力
- 中英文都能识别（RapidOCR + jieba 无关，纯 RapidOCR）。
- 适合场景：蓝屏代码、报错信息、弹窗提示等**截图文字**。

### 能否分析蓝屏截图 / 错误代码 / 日志
- 蓝屏截图：能，前提是代码文字能被 OCR 识别出来，然后交给模型按知识库判断。【已实现】
- 错误代码：能，模型会结合知识库与常识回答。
- 日志：只能处理用户**复制粘贴**的日志文字；**不能**上传日志文件自动读取（无文件解析能力）。

### 能否读取用户电脑硬件信息 / 自动获取系统信息 / 运行命令 / 远程操作电脑
- **全部不能**。FixPilot 是纯问诊对话，无任何系统权限、无命令行执行、无远程操作能力。【明确】
  - 无法读取硬件信息。
  - 无法自动获取系统信息。
  - 无法运行命令。
  - 无法远程操作电脑。
  - 只能靠用户手动描述症状、或手动把系统信息/报错文字/日志复制粘贴进来。

### 能否联网搜索
- **不能**。后端只调用 DeepSeek chat/completions，无联网搜索工具。

### 是否有知识库
- 有，本地 RAG。【已实现】
  - 数据源：单个转写文本 `file/2025全球最全电脑故障解决指南(720P).txt`。
  - 切块：按 `00:00` 时间戳行切块，丢弃长度 ≤20 的碎片。
  - 检索：jieba 中文分词 + BM25（自实现），`TOP_K=6`。
  - 使用：取最近一条用户消息做查询，把命中的知识块以 `[片段]` 形式作为第二个 system 消息注入。
  - 未命中时：模型被告知「（本次未检索到相关知识块）」，System Prompt 要求「若知识库未覆盖，明确说『这个场景知识库里没有收录』，再给一个稳妥的通用建议」。

### 是否有工具调用
- **没有**。模型无 function calling、无工具链。唯一"工具"是 RAG 检索和 OCR，都是后端固定流程，非模型自主调用。

### 能否记住历史故障 / 跨对话记忆用户信息
- **会话内**：能。每次请求会把当前会话的完整历史消息（含图片）发给模型，模型上下文内"记得"本次对话的过程。【已实现】
- **跨对话**：不能。没有用户画像、没有长期记忆、没有跨会话记忆（见第 7 节）。不同对话之间互不共享上下文。
- 换个用户/换台设备登录，也互不影响（数据按邀请码隔离）。

### 目前使用什么模型 / API
- 默认：DeepSeek `deepseek-v4-flash`，`DEEPSEEK_BASE_URL=https://api.deepseek.com`。
- 流式：`/chat/completions`，`temperature=0.8`，`max_tokens=1500`，SSE 输出。
- 用户可配置自定义 API（DeepSeek 或 OpenAI 兼容任意基址/模型），走用户自己额度，跳过配额扣减。【已实现】

### 模型理论上能做到 vs 产品实际开放
| 能力 | 理论可能 | FixPilot 实际开放 |
|------|:---:|:---:|
| 看图（视觉理解硬件/接线） | 多模态模型可以 | **否**，只用 OCR 文字 |
| 联网搜索 | 通过工具可以 | **否** |
| 运行命令 / 远程操作 | 通过工具/系统权限可以 | **否** |
| 读取硬件/系统信息 | 通过 agent 可以 | **否** |
| 跨会话长期记忆 | 通过向量记忆/画像可以 | **否** |
| 工具调用 / function calling | 模型能力 & 框架支持 | **否** |
| 处理日志文件 | 可以（解析文件） | **否**，只能粘贴文字 |
| 知识库检索 | 有 | **是**（BM25 本地） |
| 图片 OCR 文字 | 有 | **是**（RapidOCR 本地） |

## 4. 当前故障诊断逻辑

> 以下规则主要来自 System Prompt（llm.py 的 SYSTEM_PROMPT），【已实现】。

### 核心：交互式问诊，一次只问一个关键问题
- System Prompt 原文：
  ```
  一次只推进一小步。先根据用户描述判断最可能的方向，用一句话说清方向，
  然后用【1 个】清晰的关键判断题引导用户回答
  （例如"大小写键的灯亮不亮？""开机风扇转不转？""能不能进 BIOS？"）。
  等用户回答后再进入下一步。
  ```
- **先给方向判断，再问一个问题**，不一次性罗列完整排查流程。

### 用户只说「电脑蓝屏了」时
- 按问诊逻辑：先判断最可能方向（驱动/系统/硬件），用一句话说清方向，再问一个判断题（结合知识库），如「蓝屏前在做什么？是开机就蓝还是用着蓝？」。不直接堆一大堆排查步骤。

### 用户发错误截图时
- 先 OCR 提取文字 → 把识别文字作为图片文字来源注入 → 模型据此结合知识库判断方向 → 问一个判断题。

### 信息不足时先问什么
- 问最能区分方向的关键判断题，一次一个，选项一般 2-4 个（见下）。

### 是否要求一次只问一个关键问题
- **是**，硬性要求。同时要求回复末尾必须带 `选项：` 可点选选项（2-4 个），覆盖常见情况。
- 例外：`只有极少数纯粹开放性的描述才允许不写「选项：」`。

### 是先给结论还是先收集信息
- 混合问诊式：**先给一个方向性结论/判断**（简短），**再问一个判断题**收集信息；用户回答后再推进。不一次性收集完所有信息。

### 如何表达诊断概率
- **当前没有明确规则**。System Prompt 未规定用百分比或「可能/大概率」等措辞。【未确定】
- 唯一相关约束：知识库未覆盖时明确说「这个场景知识库里没有收录」。

### 如何避免把可能原因说成确定原因
- **当前没有明确、系统的规则**。仅靠「先判断最可能方向 + 逐步验证 + 知识库优先」来间接降低武断。是否要用「可能/大概率」等措辞没有硬性规定。【未确定】

### 软件问题和硬件问题分别怎么排查
- 没有独立成文的软件/硬件排查分支规则。由模型根据知识库 + 问诊自行判断。知识库转写稿本身按「阶段/分类」组织（见 mindmap 的 9 大分类：开机不通电、通电黑屏、进不了系统、蓝屏卡死、花屏闪屏、使用中常见问题、装系统、重装常见问题、系统优化）。【已实现的是知识库内容，软硬件分支策略未单独成文】

### 高风险操作如何处理
- **当前没有任何高风险操作确认机制**。System Prompt 未提及 BIOS、注册表、格式化、重装等的二次确认或警告（见第 8 节）。

### 什么情况下应该停止继续远程指导
- **当前没有明确规则**。【未确定】

## 5. 当前 AI 人格与语言风格

> 以下均来自 System Prompt（llm.py），【已实现】。

### FixPilot 给人的感觉
- 专业电脑故障排查助手，像医生问诊；整体语气损一点、调侃一点、带点冷幽默，像损友，但本质是真心帮你修好电脑。

### 正常情况下怎么说话
- 交互式、简短（单次 100~150 字，最多 200 字），知乎体排版（短段落，段间空一行；步骤每步单独成行、`1. ` 开头；关键结论加粗；提示用 `> 引用`）。
- 全程中文。

### 是否允许开玩笑
- 允许，但只在合适时机「皮一下」，不每条都损。

### 是否允许毒舌
- 允许，有条件：

## 9. 已经确定的产品原则

### 【明确确定】
- **禁止使用任何 emoji 表情符号**（铁律）。
- **禁止使用中间点 `·` 及 `• ● ◦ ‣ ・` 等装饰性圆点符号**（铁律，防 iPhone/部分字体乱码方框）。替代：并列词用顿号、备选/键位用斜杠、标题用连字符 ` - `。
- **交互式问诊，一次只推进一小步，一次只问一个关键判断题**，不输出长篇、不写成教程。
- **回复简短**（100~150 字，最多 200 字）。
- **毒舌但专业**：只在低级错误时损，损完立刻给下一步；不人身攻击、不脏字、点到为止。
- **识图只能 OCR 文字**，不能"看图"；用户要看硬件/接线时坦诚说明并引导文字描述。
- **无关图片友善引导**，不指责、不追问为什么发无关图。
- **主题引导宽松**，面向朋友，不硬拒绝，电脑延伸话题正常聊、尽量往维修靠。
- **额度用完/过期不清空聊天记录**，只在对话末尾追加提示条。
- **收藏星标不假装收藏**：尝试浏览器书签 API，现代浏览器无法操作时只提示 Ctrl+D，不填充星星。
- **分享页/长图**：生成长图用本地 html2canvas，不依赖外网；分享为只读链接。
- **账号绑定软引导**：不强制，邀请码登录后零摩擦进主界面，绑定入口自愿（记忆中是"绑定账号按钮"，当前实现为首提问后的提示条）。
- **自定义 API 保存前先测试连通性**，失败不保存并给中文错误提示。
- **输入框**：默认高度约单行 3 倍、占位符左上角、内容超高整体向上长高、按钮沉底。
- **玻璃拟态悬浮 UI**，移动端卡片贴满全屏；登录页与主界面风格统一。
- **排版细节执念**（用户强偏好）：正文两端对齐、标题独字不成行、标题超长省略、左右留白对称、hover 才显示操作、用图标而非中文标签、链接卡片浅灰边框深色标题无下划线、大纲动态宽度等（详见用户 profile，属 UI 细节，不完全对应产品规则）。

### 【倾向如此】
- 用户电脑水平分三档（不太懂/会折腾一点/比较熟），语气分三档（正常/嘴毒/少废话），在首次进入的欢迎对话框里用卡片选择。倾向做成两屏选择流程。
- 欢迎对话框倾向用简单开场语，不放「图片只能 OCR」这类提示。
- 表情包倾向集成到低级错误场景（file/img 那 9 张嘲讽系）。

### 【讨论过但没定】
- 自动推断用户水平（观察几次有效对话）。
- confidence 置信度机制。
- 用户主动选择 vs AI 自动判断谁优先。
- 是否允许后续动态修改水平。
- 语气/水平是否与回答深度自动联动（"专家也也会用我们的功能"用户提过，细则未定）。

【说话风格：毒舌但专业，有趣不伤人】
- 整体语气：损一点、调侃一点、带点冷幽默，像个损友，但本质是真心帮你修好电脑。
- 只在对方犯明显低级错误或闹乌龙时才毒舌...而且必须把吐槽建立在事实上，不要凭空讽刺。
- 毒舌三要素（必须同时满足）：
  1. 吐槽要生动、具体、好笑，可以夸张...
  2. 吐槽完必须立刻接上正事，给出当前这一步该怎么做，绝不光损不办事。
  3. 永远不要人身攻击、不骂人、不带脏字、不阴阳怪气到让对方下不来台；朋友式互损，点到为止。
- 毒舌要控制频率：不是每条都要损，正常交流还是专业耐心为主，只在合适时机皮一下，效果最好。
- 「6」彩蛋标记：当你判断用户犯了明显低级错误或闹乌龙时...在回复的第一行单独输出一行 `[JOKE6]`...
- 严禁使用任何 emoji 表情符号，也不要用任何圆点装饰符号（用顿号、斜杠、连字符替代）。
```

**识图边界（原文）：**
```
- 你的识图能力边界：你只能读取图片里的"文字"（OCR），不能真正"看"图。
  如果用户想让你通过图片判断硬件外观、接线是否正确、屏幕画面等需要"看图"的内容，
  要坦诚说明这一点，然后引导用户改用文字描述症状或把关键报错文字发给你。

### 关键伪代码 / 逻辑片段

**RAG 编排（service.chat_stream）：**
```
1. 把所有消息 content 转纯文本；图片消息调 ocr.image_to_text(dataURL) 提取文字，
   标注为 "[用户上传图片中的文字]\n..."（OCR 失败则占位，不阻断）。
2. 取最近一条 user 消息作为查询 → retriever.retrieve(query)（jieba+BM25，TOP_K=6）。
3. 组装：system(SYSTEM_PROMPT) + 历史消息 + 在最后一条 user 前插入 system(知识上下文)。
4. llm.stream_chat 流式返回。
```

**聊天入库与 JOKE6（main.gen）：**
```
流式收集 token → 完成后：
  db.add_message(conv_id, "user", user_text, user_image)
  若正片以 "[JOKE6]" 开头：
      db.add_message(conv_id, "assistant", "6")          # 先存"6"
      db.add_message(conv_id, "assistant", 剥掉标记的正文)  # 再存正片
  否则：db.add_message(conv_id, "assistant", 整体正文)
  若是邀请码用户且未用自定义API：invite_codes.quota_used += 1
```

**配额判定（auth.can_use）：**
```
if 邀请码已过期(expires_at < now): return (False, "expired")
if quota_total != -1 且 quota_used >= quota_total: return (False, "exhausted")
return (True, "ok")
```
> 注意：邀请码登录**即使次数用完/过期也允许登录**，由前端显示提示条引导用户填自己的 API 继续用。

**前端选项按钮（app.js parseOptions / renderBotMsg）：**
- 正则匹配 `选项\s*[:：]` 切分正文与选项。
- 支持同行连写 `1.xxx2.yyy3.zzz` 拆分为多个按钮（`\d+[.、)]`）。
- 泛化选项（金都「其他/都不是/我来描述」等）视为"其他"入口，点击只聚焦输入框不发送，避免浪费 token。
- 固定追加一个「其他」按钮。
- 选项点击后：普通选项直接作为消息发送；收缩动画（collapsing）后消失。

**编号列表自动分行（app.js breakNumbered）：**
- 把正文里同行连写的 `1.xxx2.yyy3.zzz` 用正则 `([^\n])(\d+[.、)])(?!\d)` 拆到新行，不影响小数（3.5mm）与已有空行。

**前端 SSE 解析（app.js send）：**
- 后端用 `json.dumps(token)` 编码每个 token，SSE 事件边界 `data: ...\n\n`；前端 `JSON.parse(data)` 解码还原 Markdown。
- 事件：`data:__start__` 开始、`data:__end__` 结束、`data:__error__:<msg>` 出错。
- 流式过程中检测 `[JOKE6]`：命中则清空已收内容、`showJoke6()` 播放"6"彩蛋，之后追加新气泡显示正片。

**前端自定义 API 流程（app.js saveApiSettings_action）：**
- 填 Key → 先 `POST /api/test-api`（发一条极简请求）→ 通过才 `saveApiSettings` → 更新模型选择器与额度显示。
- 后端 401=Key 无效、403=无权限、404=地址/模型不存在、429=限流、5xx=服务端异常，翻译成中文提示。
