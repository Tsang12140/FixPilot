# 测试工作流

## 目的

测试不是证明脚本能退出，也不是让 AI 猜“应该没问题”。测试要回答：

- 这次改动实际覆盖了什么用户路径？
- 正常、失败和边界输入分别会怎样？
- 结果是通过、产品缺陷、基础设施失败，还是需要人工判断？
- 如果发现问题，后来的人如何复现、修复和验证？

## 触发约定

收到“我要测试”“跑测试”“回归测试”“测一下”时：

1. 先读 AGENTS.md、ai/WORK_LOG.md、本目录 README.md 和当前项目测试档案。
2. 根据用户刚提到的功能或 Bug 推断测试范围；范围真的不清楚时，先问要测哪个功能或是否做发布前全量回归。
3. 不得把 py_compile、页面能打开、HTTP 200 或脚本没有崩溃，单独当作产品通过。
4. 先声明要跑哪些模块、是否会消耗模型额度、产物放在哪里；再执行。
5. 任何失败都保留最少复现证据：用例 ID、输入、会话/请求关联号、状态、可见结果和日志位置。不得记录密码、API key 或 token。

## 六个阶段

### 1. 建基线

记录当前分支、最近提交和现有未提交改动。确认目标服务地址、账号权限、外部模型成本和被测版本。不要为了测试清理用户的工作区。

### 2. 选择模块

按项目测试档案选择最小充分集合。

- 改对话、模型接入、流式解析：传输与会话连续性。
- 改提示词、人格、画像、诊断流程：动态人设和诊断方向。
- 改 OCR/图片：图像输入和失败降级。
- 改危险操作或安全文案：风险分级和停止指导。
- 改认证、分享、管理员功能：权限和注入边界。
- 发布前：档案指定的全量回归。

不能只测用户报告的那一个例子。每个已确认 Bug 都要按同类路径补一条回归检查。

### 3. 运行并留证

每次真实运行都产出结构化 JSON。结果记录不得含凭据。长对话、陪练模型或联网步骤会花钱时，先跑目标模块；发布前全量由用户决定。

### 4. 严格分类

| 状态 | 含义 | 是否可宣布通过 |
| --- | --- | --- |
| PASS | 用例的可观察契约全部满足 | 可以 |
| FAIL | 产品行为或安全契约不满足 | 不可以 |
| ERROR | 网络、鉴权、SSE、服务、测试设置等导致无法判断产品 | 不可以 |
| REVIEW | 技术护栏存在，但生成文案/结果需要人工判读 | 不可以 |

ERROR 不是 PASS。REVIEW 也不是 PASS。HTTP 200 但 SSE 返回错误、空回复或只有内部推理，都应归 ERROR。

### 5. 修复与回归

修一个 Bug，至少验证：

1. 原始复现路径已通过。
2. 同类/镜像路径没有被遗漏。
3. 新的兜底没有误伤正常输入。

实际修好的单项 Bug：追加 reports/fixed.md。
一次批量检索或批量修复：另外写 reports/reportYYYYMMDD_NNN.md。
每个完整任务：追加 ai/WORK_LOG.md。三份记录职责不同，不能互相替代。

### 6. 交接

交接要写清：

- 已跑/没跑的模块和原因。
- 结果、报告位置、失败/人工复核项。
- 运行命令的结构，但永远省略敏感值。
- 哪些结论是实测，哪些只是静态检查。

## 复用原则

通用层可复用：认证、会话创建、请求发送、流解析、产物、结果状态。
项目层不可照抄：真实业务场景、风险分级、正确答案、人工复核标准、模型成本和隐私边界。

在新项目中复制 PROJECT_TEST_PROFILE.template.md 和本工作流，并把项目根目录 AGENTS.md 的“测试工作流触发”规则一并复制。然后先写该项目的真实测试档案，最后才写测试脚本。
